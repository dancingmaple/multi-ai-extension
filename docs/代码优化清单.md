# 多 AI 工作台扩展 · 代码优化清单

> 审查范围：worktree `260508-web-multi-ai-workbench2`（分支 `feat/workbench2`），约 1.46 万行。
> 模块：background(2375) / content(3555) / shared(1415) / sidepanel(2640) / workbench(3993) / workbench-test(691)。
> 说明：行号基于审查时快照，后续改动可能略有偏移；同一问题在多模块出现的已合并并标注各处。

---

## 总体评价

- **架构清晰**：执行双路径（内嵌 iframe / 标签页）+ DAG 工作台 + 侧边栏并排视图，分层合理，纯函数（workflowUtils）与适配器基类抽象到位。
- **三大系统性风险**：① MV3 Service Worker 生命周期导致 in-flight 状态丢失（多模块各自零散修补，缺统一机制）；② postMessage 全链路无 origin 校验（安全洞）；③ storage read-modify-write 普遍无锁（并发覆盖）。
- **可维护性瓶颈**：`workflowStore.ts`(1223 行, 40+ 成员) 与 `WebView.tsx`(624 行, 9 useRef) 过度膨胀；适配器间大量重复 DOM 工具函数。

## P0 · 必修（影响安全 / 数据一致性 / 主流程可用性）

### 1. 【安全】postMessage 全链路缺 origin 校验
- `content/index.ts:200-307`、`sidepanel/WebView.tsx:111,123,322`、`workbench/embedBridge.ts:113-168`
- 任意第三方网页嵌入本扩展 iframe 即可伪造 `EXECUTE`（向付费 AI 发任意 prompt）、`GRAB`/`PICK_START`（读屏泄露对话）、`EXECUTE_DONE`（注入虚假回答）。`replyTo` 与 WebView 下发均用 `'*'` 广播，回答可泄露给恶意父页。
- **方向**：listener 入口维护 origin 白名单（`chrome.runtime.getURL('/')` + 各 provider origin），不在白名单的 `ev.origin` 直接 return；`postMessage` 第二参传具体 origin（`new URL(url).origin`）而非 `'*'`；`embedBridge.dispatch` 校验 `ev.source` 是否为已注册的 iframe contentWindow。

### 2. 【工作台】执行链可永久卡死（pendingContinue / runNode / confirmNode 竞态）
- `workbench/store/workflowStore.ts:652-655, 637-649, 727-857`
- `awaitingConfirm` 暂停期间用户手动 `runNode` 会清空 `pendingContinue` 但保留 `running=true`，之后点「采纳」永远无法恢复，运行按钮永久 disabled；`confirmNode` 对 error/idle 节点也触发 `pendingContinue`，带 error 节点继续连锁失败；`executeNode` 不检查全局 `running`，可被并发调用致状态机紊乱。
- **方向**：`runNode` 入口检查 `awaitingConfirm`，为 true 则先重置 `running/awaitingConfirm` 或拒绝并提示；`pendingContinue` 恢复逻辑移入 `reviewing/success` 分支内，新增独立 `skipNode`；`executeNode` 加 `if (get().running && !get().awaitingConfirm) return` 守卫。

### 3. 【MV3】SW 重启后 in-flight 任务 / 映射表丢失（系统性）
- `background/conversationStore.ts:22`（`taskToConversationId` 不持久化 → `sedimentTask` 失效，回答不沉淀）、`background/stateStore.ts:4,168`（`tasks` 只持久化 `lastTask` 单条 → 并发多 task 全丢）、`background/trustedClick.ts:10,67`（debugger 会话残留 + `attachedTab` 单例不支持并发）、`workbench/store/workflowStore.ts:385`（页面重载后 `running` 节点永久卡死，`executingNodes` 丢失）。
- **方向**：统一做「active tasks + 反向映射」持久化与恢复机制——`taskToConversationId` 落盘或从 `conversations[*].turns[*].id` 反向重建；`stateStore` 持久化 `activeTasks` 数组，完成后移除；SW 启动时 `chrome.debugger.getTargets` 探测并 detach 残留会话，`attachedTab` 改 `Map<tabId, Promise>` + `tabs.onRemoved` 清理；`load()` 将 `status:'running'` 节点重置为 `error`（附「重载中断」提示）。

### 4. 【工作台引擎】deadline 兜底失效，极端情况下请求永久挂起
- `background/workbenchEngine.ts:92,100` + `messageRouter.ts:488-496`
- `await handleAskAll` 内部 `Promise.allSettled(dispatches)`，单 provider dispatch 最坏 55s+（tab ready 30s×2 + sleep 3s + script ready 5s + sendMessage 20s）。若 `maxPer` 较小（deepseek 45s → deadline 53s），`handleAskAll` 超过 deadline，`waitForSettled` 永不执行，请求永久挂起。
- **方向**：不 await `handleAskAll`，先 fire dispatch 再立即启动 `waitForSettled`；或 `Promise.race([handleAskAll, sleep(deadline)])`。

### 5. 【MV3】SW 冷启动期间需响应消息被吞
- `background/messageRouter.ts:210-218`
- SW 冷启动期到达的 `WORKBENCH_EXECUTE`/`EXPORT_MARKDOWN`/`MANUAL_GRAB` 等需返回值消息，`doInit` 后处理时 `sendResponse()` 无参、返回值被 `catch(()=>{})` 丢弃，前端收到 `undefined` 判定失败/卡死。
- **方向**：`const resp = await handleUIMessage(msg,sender).catch(e=>({ok:false,error:String(e)})); sendResponse(resp);`。

### 6. 【content】sessionStorage 恢复执行不重新校验 provider
- `content/index.ts:321-335`
- `location.assign` 后脚本重注入，立即从 sessionStorage 取 msg 调 `runExecute`，**不再走 `accepts()`**。若站点重定向到登录页或非目标页，仍强行用原适配器操作错页面。
- **方向**：恢复前重新 `getProviderFromUrl(location.href)` 与 `msg.provider` 比对，不匹配则丢弃并回传 `EXECUTE_ERROR`。

### 7. 【性能】MutationObserver 全文档监听致 CPU 飙升
- `content/dom/observer.ts:25-37` + `chatgpt.ts:342`/`deepseek.ts:268`/`doubao.ts:365`/`zai.ts:148`/`gemini.ts:612`
- 监听 `document.body` + subtree + characterData，长对话流式期间每秒触发数十次，每次 tick 全文档 `querySelectorAll('[class*="markdown"]')` + `closest`，叠加 400ms 轮询，主线程阻塞致卡顿。
- **方向**：observer 只观察「最后一条 assistant 节点」（拿到后 `observer.observe(msgEl)`，新 assistant 出现时切换）；流式期间禁用 polling 仅靠 observer；`cgFindThinkingHeader` 的 `querySelectorAll('*')` 限制搜索深度。

### 8. 【数据一致性】自定义 provider/selector 与历史的 storage 写竞态
- `shared/customProviders.ts:43-63`、`shared/customSelectors.ts:35-63`、`background/messageRouter.ts:68-80`（`persistStream`）、`messageRouter.ts:110-115`（`saveToHistory`）
- read-modify-write 无锁，多标签页（侧边栏+测试台+工作台）同时写或并发 provider 流式时后写覆盖先写，丢自定义配置 / 流式快照 / 历史条目。
- **方向**：写操作收口到 background 串行处理，或用 `navigator.locks`（MV3 支持）加进程内锁；`persistStream`/`saveToHistory` 改内存维护 + 节流落盘。

## P1 · 重要（性能 / 健壮性 / 可维护性）

### 9. 【工作台】无执行取消/中止机制
- `workflowStore.ts` 全局：`runFrom` 循环无取消信号，节点卡 running 只能等 140/150s 超时或刷新。
- **方向**：引入 `AbortController`/`cancelled` 标志，`runFrom` 每轮检查；工具栏加「停止」按钮。

### 10. 【工作台】流式更新触发全量 nodes 重建 + 全组件重渲染
- `workflowStore.ts:294-302,613-619`（每 chunk `set({nodes: get().nodes.map(...)})` O(N)）；`EmbeddedRunner.tsx:22`、`SessionDock.tsx:149` 订阅整个 `nodes`。
- **方向**：stream 更新节流 100ms 合并；节点组件用 `useWorkflowStore(s => s.nodes.find(n=>n.id===id))` 精细订阅；EmbeddedRunner/SessionDock 用 `useShallow` 选择器只取 provider 集合/必要字段。

### 11. 【工作台】`buildOutputMap`/`buildVarMap` 缓存永远不命中（死代码）
- `workbench/store/workflowUtils.ts:216-252`：`outputKey()` 每次产出新数组，`k === key[i]` 引用比较恒 false，缓存形同虚设。
- **方向**：改为 `nodes` 引用比较（`cache.nodesRef === nodes`）或序列化字符串 key。

### 12. 【工作台】内嵌执行超时后 embedBridge.pending 内存泄漏
- `workflowStore.ts:307-309` + `embedBridge.ts:88-95,134-150`：150s 超时 `finish` 后 `pending[taskId]` 未清理。
- **方向**：`finish` 内调 `embedBridge.cancel(taskId)`；embedBridge 增 `cancel(taskId)` 方法。

### 13. 【工作台】`grabEmbedNode` 串行抓取，N 家耗时线性叠加
- `workflowStore.ts:336-361`：`for...of` 串行，每家最多 45s，3 家最坏 135s（而 runEmbedNode 是并行的）。
- **方向**：改 `Promise.allSettled` 并行，与 runEmbedNode 一致。

### 14. 【工作台】`runWorkflow` 全量重置丢失已审阅结果
- `workflowStore.ts:859-879`：每次运行重置所有节点为 idle 并清空 outputs，无法只重跑某节点之后的部分。
- **方向**：增 `runFromNode(id)`，仅重置该节点及其下游。

### 15. 【工作台】`WorkflowState` 接口过载（40+ 成员，1223 行）
- `workflowStore.ts:481-571`：编辑/执行/持久化/历史/预设/浮层/dock/embed 全混，难单测难局部订阅。
- **方向**：拆 `useCanvasStore`/`useExecutionStore`/`useHistoryStore`，各自独立持久化。

### 16. 【工作台】`loadSavedWorkflow`/`applyPreset` 未 sanitize 节点
- `workflowStore.ts:996-1001,1079-1089`：直接 `set({nodes: wf.nodes})`，未过 `sanitizeNodes`，ReactFlow 瞬态字段（measured/selected/dragging）带入画布致异常。
- **方向**：加载时统一过 `sanitizeNodes`，与 `save` 对称。

### 17. 【background】`getOrCreateProviderTab` 无 in-flight 去重 → 孤儿 tab
- `tabManager.ts:84-108`：同 (nodeId,provider) 快速二次触发，两调用都见 `existing===undefined` 各自 create，后写覆盖登记表，先创建的永不复用不清理。
- **方向**：`Map<string, Promise<number>>` 同 key 复用 Promise。

### 18. 【background】`handleAskAll` 无幂等/去重
- `messageRouter.ts:488-496`：同 taskId 重复触发仍全量 `dispatchToProvider` 重发。
- **方向**：检查 task 是否已有 in-flight provider，跳过；对 taskId 加执行锁。

### 19. 【background】`conversationStore.ensureLoaded` boolean 标志竞态
- `conversationStore.ts:36-46`：第一个调用设 `loaded=true` 后 await，第二个见 true 直接返回但 Map 仍空，`getConversation` 返回 undefined。
- **方向**：`let loadPromise: Promise<void>|undefined; await (loadPromise ??= doLoad())`。

### 20. 【background】`deleteTask` 后慢 provider 的 `TASK_DONE` 回答被静默丢弃
- `workbenchEngine.ts:141` + `stateStore.ts:96`：deadline 超时 `deleteTask` 清理，迟到结果因 `tasks.get` 返回 undefined 直接 return，无日志。
- **方向**：deleteTask 延迟宽限期（deadline 后再等 5-10s），或对迟到结果兜底日志/回调。

### 21. 【background】`customSite` 三事件触发 `syncCustomSites` 无 mutex
- `customSite.ts:120-133`：批量授权/连续编辑时多个 sync 并发，`unregister`/`register` 交错致脚本未注册或注册过期集合。
- **方向**：`let syncPromise`，后续调用复用 in-flight 或排队。

### 22. 【content】基类 `startStreaming` 默认实现是已知坏范式
- `content/adapters/base.ts:126-186`：注释明确「拿到上一轮 assistant 即判完成」，所有适配器被迫 override，新增适配器忘 override 即复现 bug。
- **方向**：基类改为抽象方法，或在基类实现「提交快照门闩」范式（custom.ts 是范本）强制统一。

### 23. 【content】适配器间大量重复 DOM 工具函数
- `isVisible`/`readBack`/`writeExec`/`writeOk`/`fireEnter`/`findVisibleInput` 在 8 个适配器逐字复制（`shared/utils.ts` 已有 `setNativeInputValue` 等但未被用）。
- **方向**：抽 `shared/domUtils.ts` 统一复用。

### 24. 【content】大量魔法延时且无取消机制
- `gemini.ts:323-381`（submit 最坏阻塞 13s）、`gemini.ts:154`（sleep 1000）、`doubao.ts:241`（sleep 400）、`kimi.ts:185-224`（TRUSTED_CLICK 无超时）。
- **方向**：「等按钮 enabled」改 MutationObserver 监听 disabled 变化（带超时兜底）；submit 接 AbortSignal；kimi 的 sendMessage 包 `Promise.race([, sleep(8000)])`。

### 25. 【content】`executor` 适配器单例 + settings 缓存不失效
- `executor.ts:16-41`：模块级单例，`clearSettingsCache` 是死代码，用户改设置需重载扩展；异常未走完时下次复用残留 customSelectors。
- **方向**：每次 `resolveAdapter` 返回新实例，或 setTimeouts 时重置 customSelectors；监听 `storage.onChanged` 让缓存自动失效。

### 26. 【content】登录检测过于脆弱
- `base.ts:78-86,97-99` + 各适配器 `loginSelectors`：`text === pattern` 全等 + `a[href*="login"]` 子串匹配，`'登录 Google'`/`/docs/login-guide` 全漏判/误判。
- **方向**：改 `text.includes(pattern)` 忽略大小写空白；href 用严格正则 `/(^|\/)(login|signin|auth)(\/|$|\?)/i`。

### 27. 【shared】`ProviderName = string` 让内置表类型形同虚设
- `shared/types.ts:9`：`custom:xxx` 与 `'chatgpt'` 同 namespace，编译期无法捕获拼写错误。
- **方向**：`ProviderName = BuiltinProviderName | \`custom:${string}\`` 模板字面量类型。

### 28. 【shared】storage 访问无内存缓存
- `providers.ts:39-74`、`customProviders.ts:13-22`、`customSelectors.ts:10-19`：每次直接 `storage.local.get`，content script 解析 provider / `useEffectiveProviders` 链路在每次状态变更都全量读盘，冷启动串行 await 拖慢首屏。
- **方向**：module-level Promise 缓存 + `storage.onChanged` 失效；`getEffectiveProviders` 返回缓存后同步值。

### 29. 【sidepanel】`WebView.tsx` 过度膨胀（624 行, 9 useRef, 6 useState, 5 类 timer）
- per-provider 字典（frameRefs/frameReady/pendingSend/stallTimers/embedTimers/grabTimers/grabReq）散落，unmount 易漏清。
- **方向**：抽 `useEmbedFrame(provider, url)` hook 封装单 provider 的 ready/pending/stall/grab 状态。

### 30. 【sidepanel】`isLoading` 可能卡死 5 分钟
- `store.ts:498-539,372-405`：只在异常/5 分钟兜底清除，正常路径依赖 App.tsx 副作用；background 崩溃/tab 关闭/消息丢失时卡到 5 分钟。
- **方向**：store 内部监听 `TASK_STATE_UPDATE` 全部 settle 时主动 `clearTimeout(safetyTimer)`。

### 31. 【sidepanel】`HistoryList` 无虚拟化
- `HistoryList.tsx:121-138`：MAX_HISTORY=200 全量渲染，每条 row 内嵌 7 家 provider 链接 = 1400 个 `<a>`，滚动卡。
- **方向**：`react-window` 或 `IntersectionObserver` 懒渲染。

### 32. 【shared】`sendToBackground` 返回 `Promise<unknown>`
- `messaging.ts:19-22`：store 里 9 处 `as {...|undefined}` 断言，background 返回结构变更时编译期不报错。
- **方向**：`sendToBackground<T>(msg): Promise<T>`，为每条 message 定义 request/response 对偶类型。

### 33. 【content】`pickElement` 选择器算法对 UI 微调极脆弱
- `pickElement.ts:18-37`：优先 `:nth-child(index)`，网站改版即失效。
- **方向**：优先 `data-testid`/`aria-label`/`role`/`name`，nth-child 兜底；保存多套候选运行时按序尝试。

## P2 · 改进（可维护性 / UX / 细节）

### 40. 【background】`waitForTabReady` 每 500ms 轮询 `chrome.tabs.get`
